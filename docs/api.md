# REST API contracts

Interactive documentation is generated by FastAPI at `/docs`; machine-readable OpenAPI is `/openapi.json`. All `/api` resources except login/logout require authentication. Errors return `{"detail": "Human-readable message"}`; validation errors use Pydantic's field error list. Conflict responses use 409; unauthorized/forbidden use 401/403. UUID path parameters are validated.

## Authentication

- `POST /api/auth/login`: `{email,password}` → sanitized user, HttpOnly `nmip_session` cookie.
- `GET /api/auth/me`: current sanitized active user.
- `POST /api/auth/logout`: clears cookie.

JWT bearer authorization is also accepted for API clients. Browser authentication uses the cookie, not localStorage. Login does not return the token in its response body.

## Catalog and processing

- `GET /api/organizations`
- `GET /api/materials`: filters `q`, `organization` (code), `category`, `status`, `decision`, minimum `confidence` (completeness), `grade`, `standard`, `common_identity`, `date` (ISO date lower bound).
- `POST /api/materials`: `{organization_id,legacy_material_code,original_description,category,override_reason?}`. Steward/admin; backend rechecks duplicates. Existing source code always rejected.
- `GET /api/materials/{id}`: material plus attributes and evidence.
- `PUT /api/materials/{id}`: `{original_description,reason}`. Steward/admin; verified records are locked.
- `POST /api/materials/{id}/attributes`: `{attribute_name,value,source_text,source_file,reason}`. Engineer/steward/admin; the supplied value must appear in source text. Decisions are recalculated.
- `POST /api/materials/{id}/normalize`, `/extract`, `/enrich`: steward/admin processing.
- `POST /api/pipeline/{normalize|extract|enrich}`: batch-process unverified records.

## Ingestion

- `POST /api/datasets/upload`: multipart `organization_id`, `file`; 10 MB, 10,000 rows. Returns dataset ID, columns, first ten source rows.
- `GET /api/datasets`, `GET /api/datasets/{id}`
- `POST /api/datasets/{id}/validate`: object mapping target field names to source column names. Required targets: `legacy_material_code`, `original_description`, `category`; optional `unit`, `manufacturer`, `specification`, `standard`.
- `GET /api/datasets/{id}/validation`: rows with values/errors and valid/invalid counts.
- `GET /api/datasets/{id}/validation.csv`: downloadable report.
- `POST /api/datasets/{id}/import`: revalidates against current source codes and imports valid rows atomically. Imported datasets cannot be imported twice.

## Candidates, decisions and review

- `POST /api/candidates/retrieve`: `{material_id?:UUID,top_n?:1..20}`. Omitting material retrieves for the processed catalog. Returns actual persisted candidates.
- `GET /api/candidates`, `GET /api/materials/{id}/candidates`
- `GET /api/candidates/{id}/comparison`: source materials, decision snapshot, comparisons, evidence, reviews.
- `POST /api/candidates/{id}/decision`: engineer/admin; creates a new decision snapshot. Approved decisions cannot be rerun.
- `POST /api/reviews`: `{decision_id,action:APPROVE|REJECT|REQUEST_INFORMATION,comment}`. Engineer/admin. Current material/rule snapshot required. Only IDENTITY_MATCH approval creates an identity.

## Identity governance

- `GET /api/common-identities`, `GET /api/common-identities/{id}`
- `POST /api/common-identities`: `{decision_id}`; requires an already-approved identity decision. Normal UI approval creates the identity atomically.
- `POST /api/common-identities/{id}/mappings`: `{decision_id}`; requires an approved pair linked to that identity. Cannot attach an arbitrary material.
- `POST /api/common-identities/{id}/publish`: publish to local NMIP catalog.
- `GET /api/common-identities/{id}/export`: JSON canonical attributes, legacy mappings, evidence and reviews. Does not contact an ERP.
- `POST /api/duplicate-check`: `{description,category}` → candidates, engineering comparisons, source references, matched common identity. Does not create material.

## Administration and measurement

- `GET /api/analytics/overview`, `GET /api/audit` (latest 1,000 events)
- `GET /api/rules`; admin `POST /api/rules`, `PUT /api/rules/{id}`: `{category,attribute_name,rule_type:EXACT|NUMERIC,rule_definition:{tolerance},severity,is_active}`
- Admin `GET /api/users`, `POST /api/users`, `PUT /api/users/{id}`. Updates accept `{role,is_active}` and cannot demote/deactivate the caller.
- `GET /api/settings`; admin `POST /api/settings/dictionary`: `{term,expansion,kind,category}`; upserts by term and increments version.
- `GET /api/proof-board`; engineer/admin `POST /api/proof-board/benchmark`: multipart CSV/XLSX `file`, columns `description_a,description_b,category,label`, up to 1,000 pairs.

## Example API session

Use an HTTP client cookie jar. Login first; subsequent requests reuse the session cookie. An engineer can POST a review with a nonempty explanatory comment after GETting the comparison. A stale snapshot returns 409 with a request to rerun the decision. The UI displays these errors without discarding the user's comment.
